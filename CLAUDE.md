# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**stoandl** is a headless Pebble smartwatch companion daemon for Linux. It bridges the D-Bus session bus (desktop notifications) to a Pebble watch over BLE via libpebble3/BlueZ. No UI. Runs as a systemd user service.

## Commands

```sh
./gradlew run          # run locally
./gradlew shadowJar    # build fat JAR → build/libs/stoandl-<version>-all.jar
java -jar build/libs/stoandl-*.jar   # run the fat JAR manually
./gradlew test                              # daemon unit tests
./gradlew :libpebble3:libpebble3:jvmTest    # the fork's JVM tests (included build)
```

Gradle 8.14.4 runs on JDK 21 (`JAVA_HOME=/usr/lib/jvm/java-21-openjdk`); Kotlin 2.4.21 compiles against a
JDK 25 toolchain, and the daemon needs JDK 25 at runtime (the Classic transport uses `java.lang.foreign`).
The versions the daemon shares with libpebble3 (the Kotlin plugins, Koin, Ktor, kotlinx, kermit) come from the
fork's `gradle/libs.versions.toml`, imported as the `forkLibs` catalog in `settings.gradle.kts`, so they move
with the submodule (the daemon compiles as the fork module's friend and must use its compiler); ical4j,
dbus-java, kotlin-logging, logback and shadow stay literals in `build.gradle.kts`. Koin is `compileOnly`, only
because upstream's public `PKJSApp` is a `KoinComponent`: the daemon never uses Koin, and `noKoinInDaemon` fails
`test` and `shadowJar` on any `org.koin.` use in `src/`, imported or fully qualified.

> Note: no `--add-opens` flags are needed. The BecomeMonitor fix reflects into dbus-java internals,
> but the fat JAR runs on the classpath where dbus-java is in the unnamed module (no encapsulation).
> Passing `--add-opens=org.freedesktop.dbus/...` only triggers a harmless
> `WARNING: Unknown module: org.freedesktop.dbus` (no such named module), so it was dropped everywhere.
> Nor does any launcher pass `--enable-native-access`: the fat JAR's manifest grants it
> (`Enable-Native-Access: ALL-UNNAMED`). Only `gradlew run` keeps it in `applicationDefaultJvmArgs`.

Install and control (requires systemd service running):
```sh
./install.sh                          # build jar (no `clean`: it drops only old fat jars), install service, restart
./install.sh --remote user@host       # build locally, copy + install on remote via SSH (an rsync delta into
                                      # the remote ~/.cache/stoandl/install when both ends have rsync)
./install.sh --remote user@host -d    # same, with debug logging drop-in
stoandl status                            # daemon, watch, services and watch tasks at a glance
stoandl apps install app.pbw              # sideload a .pbw onto the connected watch
```

## Architecture

```
Desktop apps
    │  Notify() on org.freedesktop.Notifications, AddNotification() on the portal
    │  backend (Plasma >= 6.7 Flatpaks) or org.gtk.Notifications (GNOME)  (D-Bus session bus)
    ▼
DbusNotificationMonitor   ← passive BecomeMonitor copy (does NOT intercept)
    │  Flow<IncomingNotification>  (MutableSharedFlow, buffer 64)
    ▼
PebbleIntegration / DbusNotificationListenerConnection
    │  buildTimelineNotification → libPebble.sendNotification()
    ▼
libpebble3 (composite build submodule: libs/libpebble3, stoandl branch)
    ▼
BlueZ GATT server (forward PPoG: phone acts as BLE peripheral)
    ▼
Pebble watch over BLE/PPoG
```

**Key design points:**

- `monitorNotifications()` (`DbusNotificationMonitor.kt`) uses `DBusMonitoring.BecomeMonitor` — the notification is a *passive copy*; the original still reaches the system notification daemon (dunst, mako, etc.). After `BecomeMonitor` succeeds, the writer on `TransportConnection` is replaced with a no-op via reflection to prevent dbus-java's auto-reply from closing the monitor connection. It also watches portal/GTK `AddNotification`, the server's `NotificationClosed` and `NameOwnerChanged` for its name. The server rules name `org.freedesktop.Notifications` itself, so the bus follows its owner (login, restarts) and the monitor never rebuilds for it; pending `Notify` calls are keyed by (caller, serial). The `NameOwnerChanged` rule must have no `sender=` key: dbus-broker never delivers a sender-narrowed `arg0` rule to a monitor (dbus-daemon does, so test on dbus-broker). Wrist actions go back through `DesktopNotifOwner` (`pebble/DesktopNotifOwner.kt`): Dismiss via `CloseNotification` (GNOME Shell's own object as fallback) or the backend's `RemoveNotification`; Reply and app actions via Plasma's `org.kde.NotificationManager` (`InvokeReply` needs the plasma-workspace patch and is probed by introspection) — never `InvokeAction("inline-reply")`, which KNotifications turns into an empty reply.

- `PebbleIntegration.kt` builds libpebble3 with the fork's `createJvmLibPebble(JvmHost(...))` (`io.rebble.libpebblecommon.host`, fork `jvmMain/.../host/`). `JvmHost` is the one list of what the daemon supplies: its config projection (`libPebbleConfigOf`, `pebble/LibPebbleConfigProjection.kt`), the static claims (`WatchClaims`: phone capabilities and platform flags; `syncNotificationApps` from `notification.sync_to_watch`, restart-scoped), and one factory per service: `DbusNotificationListenerConnection` (bridges the D-Bus `Flow`), the notification actions (`WatchActionRouter`, also the wrist-reply handler), time changes, MPRIS, the calendar reader, the missed-call log, the call filter (every call rings), the notification pictures, GeoClue, the phone battery and network monitors over one `PhoneState`, the Speex decoder (`voice/LibspeexFrameDecoder.kt`), find-my-phone ringing (`pebble/FindMyPhoneRinger.kt`) and plugin secrets (`PluginSecretStore::forPlugin`). Only the fork's jvm `platformModule` and actuals read it, so the graph is exactly `initKoin`'s with nothing overridden, and a new upstream platform binding becomes a new `JvmHost` parameter: a compile error here and in the fork's `KoinGraphTest` fixture at once. `createJvmLibPebble` mirrors `LibPebble3.create` but writes the host config into `LibPebbleConfigHolder` before the graph is built, so no persisted Java Preferences can override forward PPoG (`legacyReversedPPoG=false` + `useReversedPpogV2=false`), `lanDevConnection=true`, `missedNotificationCatchUpMs` (`notification.catch_up_minutes`, the fork's catch-up after a disconnect), `enablePlugins` (`plugins.enabled`) or `proactivelyDownloadAppUpdates=false` (upstream's locker prefetch, egress, pinned off). From then on `libPebble.config`/`updateConfig` is the one source of truth; a config change writes only when the projection changed, since libpebble3 persists every update. Internal services come from the returned `JvmLibPebble`'s typed doors (`linkActivity`, `watchConnector`, the notification/health/permission/vibe DAOs, `datalogging`, `plugins()`): add one only where no public `LibPebble` API covers the need. Upstream's `LibPebble.watches` is a `Flow` whose first value is the known-watches list: `util/Watches.kt`'s `StoandlLibPebble` wraps libpebble3 with one `StateFlow`, loaded once right after `init()` (`loadWatches`: a WARN at 10 s, gives up after 2 min and `Main.kt` exits 1; never an empty start, which would make every known watch look new to the pairing window). Read it with `watchesNow()`, which throws before the load or on a plain `Flow`; the BlueZ agent and shutdown, which can run during `init()`, use `watchesIfLoaded()`.

- `KermitSlf4jWriter` bridges libpebble3's Kermit logger into SLF4J/Logback. Tag names are cleaned: strips `/{...}` and `-{...}` device-path suffixes, and also plain app-name suffixes (`RhinoJsRunner-Hooky` → `RhinoJsRunner`) so logback entries match without knowing the app name.

- `SqliteNative.prepare()` (called in `main()` before `PebbleIntegration.init()`) must run before anything opens `libpebble3.db`. androidx's bundled `libsqliteJni.so` is built for glibc and imports `__isnan`; on musl the JVM's `RTLD_LAZY` load leaves it unresolved and the first REAL value in any SQL SIGSEGVs the JVM. On musl it `dlopen`s an embedded libc-free shim (`tools/isnan-shim/`, rebuilt with its `build.sh` into `src/main/resources/de/yoxcu/stoandl/natives/`) `RTLD_NOW|RTLD_GLOBAL` via FFM — `System.load` is `RTLD_LOCAL` and won't do (from the cache, else a throwaway copy in `java.io.tmpdir`). It also extracts `libsqliteJni.so` once to `~/.cache/stoandl/native/`, `System.load`s it, and only then points the driver there (`androidx.sqlite.driver.bundled.path`) instead of a new `/tmp/androidx_sqliteJni*.tmp` per start — once that property is set the driver never falls back, and loading it first from the same class loader makes the driver's own load a no-op (its `JNI_OnLoad` only registers natives on the `*Kt` facades, which have no static initialisers). Re-check all of this when bumping androidx `sqlite-bundled` (`readelf --dyn-syms` on its `natives/linux_*/libsqliteJni.so` for new glibc-only imports; `javap -c -p` on its `NativeLibraryLoader` for the property).

- `power/` makes the daemon suspend-aware for phones that deep-sleep (see [docs/deep-sleep.md](docs/deep-sleep.md)): `SleepGuard` holds a logind *delay* lock (a `systemd-inhibit … cat` child — dbus-java's native transport can't receive logind's fd) and drains pending watch traffic (libpebble3 `WatchLinkActivity`) on `PrepareForSleep(true)`: unsent notifications and the one other BlobDB transfer in flight, since the fork's BlobDB starts no non-notification transfer while `hostSuspending` is set (a hint left set past 60 s awake is ignored). `QuietTimeLink` also waits for those other records (`WatchLinkActivity.backlog`), so a pause never splits a sync; periodic work uses `delayWallClock()` (monotonic `delay()` stops while suspended) and re-checks on `SleepGuard.resumed`. Never use a *block* lock for routine work — it makes a one-shot `systemctl suspend` fail. `QuietTimeLink` (`power.quiet_time_link_off`) pauses the link during the watch's scheduled Quiet Time through the fork's in-memory `WatchConnector.holdDisconnected()`; `stoandl watch disconnect` (`pebble/ManualDisconnect.kt`) is a second hold on the same call. Never pause with `requestDisconnection()`, which persists `connectGoal=false` across restarts. The display state (`power/ScreenState.kt` `DisplayState`) is one shared flow, sampled only while a follower (the datalog pause, the Quiet Time link pause) collects it; it emits every sample, repeats included, without replay, so a follower re-syncs on the first sample after a resume. Long-lived D-Bus listeners suspend in `WatchedBus.awaitDisconnect()` (`util/DbusConnections.kt`) instead of polling `isConnected`: an idle daemon makes no periodic wakeups while awake.

- Startup takes two bus names (`Main.kt`, `PebbleIntegration.init()`): the private `de.yoxcu.stoandl.Instance` first thing, the single-instance guard `SqliteNative.prepare()` relies on (a second daemon exits there before touching anything shared), and the public `de.yoxcu.stoandl` last, once Control is exported and everything it reports has started, so a client can call as soon as it appears. The service connection (`openServiceBus()`) runs 12 method-call threads. `stoandl.conf` is watched (`config/ConfigReload.kt`): 500 ms after an edit by hand, `restore` or another process, `reloadConfig()` applies what changed since the last applied version, the same path the daemon's own writes take (`persistConfig`), and announces each key with `ConfigChanged`.

- Pairing a watch (`pebble/PairingWindow.kt` and the pair monitor in `PebbleIntegration.kt`) has ONE owner of the connect goal per watch: the Classic handler acts only on watches new to stoandl, inside a pairing window, once per window (nothing when Bluetooth is off or the bond is unreadable); known watches reconnect only through libpebble3's `connectGoal`. A window resolves only on a watch that wasn't known when it opened (a `Repair`'s watch once it has been seen without a link) and on decline or timeout gives the goal back to the watch that held it. Switching watches is manual: `Connect` (`stoandl watch connect <name>`) calls `PebbleDevice.connect()`, whose single-watch `requestConnection` sets the goal on that watch and clears and persists it on every other one (fork `WatchManagerJvmTest`); it refuses while a pairing window is open (the window's hand-back would undo it); nothing rotates the goal on its own (the wrist follower and `connection.autoswitch` were removed). The scan loop clears libpebble3's scan results once a window closes: a known watch with a leftover scan result shows as `BleDiscovered`, not known, once it loses the goal, and `startAutoConnect` would take the goal back for it.

- Text to speech is `voice/tts/` next to `voice/` (speech to text): `TtsService` runs one synthesis at a time for D-Bus `Speak` (plays on this device) and an extension's `synthesize` (audio back for the watch speaker), and `WatchSpeakerEncoding` encodes the watch-speaker blocks. `ResidentPiper` keeps libpiper's `piper_exe` loaded, one process per voice, fed `--json-input` lines; a sentence is done when its `output_file` exists and is no longer open in `/proc/<pid>/fd` (piper prints the path, but its stdout is block-buffered on a pipe, so never wait for that line). Any other Piper stays one process per sentence. The block format is binding for that encoder and the watch receiver `examples/extensions/watchlib/stoandl_speaker.c`: [docs/speaker-stream.md](docs/speaker-stream.md). Engines, players and volume tools are found with one PATH probe, `onPath` in `util/Process.kt`.

- `main()` first sets `java.net.preferIPv6Addresses=system` (the OS's RFC 6724 order: neither the JDK HttpClient nor Ktor CIO tries a second address, so IPv4-first fails on an IPv6-only mobile link). `getLoopbackAddress()` is then `::1`: local servers bind `LOOPBACK_V4` (`util/Net.kt`), the `127.0.0.1` their URLs name, and tests run with the same property. Next it sets `jdk.httpclient.keepalive.timeout=0` unless given: a pooled java.net.http connection on a suspending phone only waits for the server's idle close, whose FIN wakes it ([docs/deep-sleep.md](docs/deep-sleep.md)); the price is a connection (TCP+TLS handshake) per sequential request. The JDK reads it once, so nothing may build an `HttpClient` before that line; each PKJS session's client closes in `GraalJsRunner.stop()`. libpebble3's shared client (`createHttpClient()`, fork `jvmMain/.../js/WireBytes.jvm.kt`: plugin fetches, PKJS WebSockets, firmware and locker downloads) is on Ktor CIO, which starts no idle timer; the JDK engine would keep a selector thread waking every 3 s once first used, so keep it on CIO.

- The daemon logs to `/tmp/stoandl.log` (rolling, 5 MB × 3; tmpfs, so no flash writes) and stdout (`logback.xml`). Default level is INFO: startup, scan, watch connected, notifications, PKJS lifecycle. Set `STOANDL_LOG=DEBUG` (env var or `-DSTOANDL_LOG=DEBUG` JVM flag) for the decisions behind them (sleep guard, connect/drop reasons, catch-up, health sync); it covers all of `de.yoxcu.stoandl` and libpebble3's connection tags. The one exception is the D-Bus interfaces that nest a `DBusSignal` (`StoandlControl`, `ModemVoice`, …), capped at INFO in both logback files: dbus-java's `Message` logs its per-signal lines under the signal's own class (`getClass()`), and `LogbackSignalLoggersTest` fails for a signal interface missing there. `STOANDL_LOG=TRACE` adds a line per BLE/protocol packet (libpebble3's Kermit `v` = TRACE: keep per-packet lines there, not at `d`). The CLI never uses `logback.xml`: for any command line `Main.kt` selects `logback-cli.xml` (stderr only, WARN unless `STOANDL_LOG`) before the first logger is touched (Main's logger is lazy), so CLI calls never create or roll the daemon's log. The CLI's JVM starts from a CDS archive it writes on its first run after an install (`~/.cache/stoandl/cli-<size>-<mtime>.jsa`; `cli-*.nocds` marks a JDK or disk that can't, and the CLI then runs without it until the next install).

## libpebble3 submodule

The dependency is a patched fork of upstream [`coredevices/libpebble3`](https://github.com/coredevices/libpebble3) (`yoxcu/libpebble3`), included as a git submodule at `libs/libpebble3`. It tracks `coredevices/master` directly and is wired via Gradle composite build in `settings.gradle.kts` — no Maven publish needed. After cloning, run `git submodule update --init --recursive`.

The submodule follows fork branch **`stoandl-bump-de47e36f`**: upstream `de47e36f` (2026-11-25, 362 commits past `ec2156cc`) merged into the fork's `stoandl` as `dd37ec6a`, plus the port's fork commit (the Clear Notifications Quick Launch gate and a test of the recovery firmware install). It is a merge, not a rebase this time, so `stoandl` fast-forwards to it once its hardware pass ([TESTING §5.77](TESTING.md)) is green, with no forced push. The previous tip `a17e32d5` (base `ec2156cc`, in daily use since 2026-10-20) is the bisect baseline: tag it `stoandl-ec2156cc` when promoting. Older baselines are tagged `stoandl-bump-e6b5138e` and `stoandl-e4180ffc`; releases up to v0.8.0 recorded commits on `stoandl-rebased`. Push the fork branch, and the `gui` submodule's branch, **before** pushing a stoandl commit that records them: CI builds every push to `main` and every tag (`git submodule update --init --depth 1 libs/libpebble3`), and the APKBUILD downloads the recorded commit's archive from `yoxcu/libpebble3`, so a gitlink GitHub doesn't have yet breaks the build. [FIRMWARE-GAPS.md §3](FIRMWARE-GAPS.md) is the runbook for the next bump.

What `de47e36f` changed upstream, and how stoandl consumes it: upstream dropped its jvm target (the fork keeps it, and owns `jvmMain` outright: nothing there has an upstream counterpart any more), put the library under `explicitApi()` with most of its API `internal` (`d244beae`), turned `LibPebble.watches` into a `Flow`, took Compose and Kable out of its API, deleted `WatchConfig.enablePlugins` (`bf66a5be`), moved firmware installs that need recovery into libpebble3 (`5f24440b`), moved the language-pack list to a server manifest (`7cf80230`), removed the `language` watch pref (`b117d9a4`) and went from Room schema 49 to 54. The daemon (main and test) compiles as a Kotlin **friend** of the fork's jvm module (KGP `friendPaths` in `build.gradle.kts`, filtered to the composite's `libs/libpebble3/libpebble3/build/` output; a filter that matches nothing fails the compile), so upstream's visibility churn costs nothing. It uses a public API wherever upstream has one (`registerPlugin`, `config`/`updateConfig`, `takeScreenshot(): PebbleBitmap`, …) and internals only where none exists. A daemon class that exposes a libpebble3-internal type in its signature must itself be `internal` (the compiler says which). Everything the daemon supplies goes into `JvmHost`, and every internal service it reads comes from `JvmLibPebble` (Architecture above); there is no Koin override module and no pinned config flow any more. The IDE may show internal uses in red (it models friends only for associated compilations): the Gradle build is authoritative. The language-pack catalog (`src/main/resources/language-packs.json`) is a frozen copy of the last in-tree list (its `_origin` key names the commit); a bump no longer refreshes it, and fetching upstream's manifest would be new egress.

The fork adds: a pure-BlueZ D-Bus BLE backend + GATT server, a Bluetooth Classic (RFCOMM/SPP) transport for classic-era watches, PPoG handshake/reconnect fixes for Linux BLE (`BluezGattConnector.disconnect()` ends an attempt that is still arming, with `NotAnError_DisconnectRequested`: WatchManager's single connection slot depends on it, and a Classic attempt never ends as a `ClassicConnectionFailed`: a cancel during its RFCOMM page ends as that cancellation, a `disconnect()` as `NotAnError_DisconnectRequested`, and a socket linked meanwhile is closed; a `NotAnError_*` failure logs at DEBUG), BlueZ pairing/bonding (`classicBondState()` says when BlueZ can't tell), and a GraalJS PKJS runtime for watchapp companion JS. It builds the JVM target, with the actuals upstream no longer ships (the shared HTTP client on Ktor CIO, the plugin file system on java.nio, the PKJS runner), the `JvmHost`/`createJvmLibPebble`/`JvmLibPebble` seam, and Speex moved to `nonJvmMain` (its binding has no jvm variant; on the JVM the daemon's libspeex decodes). It also re-adds upstream's deleted `WatchConfig.enablePlugins` (default `true`, upstream's behaviour) with upstream's own pre-`bf66a5be` gates as `// stoandl:` hooks (the plugin registry and its locker loader, `AppPermissions`, `NetworkGate`, app audio streams, the locker's config page and install review), so `plugins.enabled = false` still means no plugin code runs, nothing is fetched for one, and every permission is granted. Every fork declaration is `internal`; `public actual` only for a public expect (`ForkSurfaceTest` fails otherwise). Upstream's `src/androidHostTest` stays byte-identical and is compiled into jvmTest minus a fenced exclude list in `libpebble3/build.gradle.kts` (tests bound to Android, and the two the fork twins as `WatchManagerJvmTest` and `PPoGJvmTest`); an upstream commonTest a fork test replaces is excluded the same way, never edited. jvmTest is hermetic: the same file gives it a throwaway `user.home` (`build/jvmTest-home`, emptied first) and a blank `XDG_CONFIG_HOME`, so the production Settings (Java Preferences) and the Room file database run without touching `~/.config/stoandl`. The Android-SDK-only modules sit behind one gate in its `settings.gradle.kts`: an SDK (`ANDROID_HOME` or `sdk.dir`), a Gradle at or above AGP's minimum (9.6 for AGP 9.5.x), and a standalone build, so they are never on inside stoandl's composite. The iOS targets are kept (they're load-bearing for the Room codegen).

## PKJS (PebbleKit JS)

Watchapps can ship a `pkjs/index.js` companion script. libpebble3 runs it in **GraalJS** (GraalVM JS, 25.0.x) via `GraalJsRunner`. The JS bridge initialises when the watch connects and the app is launched; look for `Pebble JS Bridge initialized.` in the log. Every context comes from one process-wide engine per HostAccess policy (`GraalEngines.contextBuilder(hostAccess)`, fork `jvmMain/.../js/GraalEngines.kt`; PKJS and plugins get one each), and the PKJS shims are `Source`s parsed once per engine, so a session starts in ~15–25 ms instead of ~50 and Truffle's per-session "fallback runtime" warning is gone. The shims (`jvmMain/resources/pkjs/startup.js`) follow upstream's Android `startup.js` minus its WebView-only realm guard and CSP: since the `de47e36f` bump PKJS also has upstream's `WebSocket` (on libpebble3's shared CIO client, refused like an XHR when the app lacks the network permission while plugins are on, and counted in the app's data usage), audio streams from the watch (`signalAudioStream`) and `Pebble.permissions.query`. The XHR follows redirects itself and checks every hop against the app's network permission before dialling it (never https→http; `Authorization` only to the origin; the `Host` header is checked too); a POST that redirects keeps the JDK's `Redirect.NORMAL` rules.

GraalJS is a full, spec-compliant ECMAScript engine — modern JS (classes, `for...of`, default/rest params, computed keys, etc.) all work. No Rhino-style syntax workarounds are needed.

> **Note:** PKJS originally ran on Mozilla Rhino 1.7.15 and was migrated to GraalJS. The trigger was Clay's `tosource()`, which runs a 60-alternative regex on every object key — pathologically slow on Rhino's NFA, fine on GraalJS's TruffleRegex DFA.

**GraalJS gotchas (build/runtime, not syntax):**
- The fat JAR **must** merge `META-INF/services/` (Shadow plugin `mergeServiceFiles()`). A plain `DuplicatesStrategy.EXCLUDE` silently drops the TruffleRegex service registration → `No language for id regex found` at runtime.
- The fat JAR **must** keep `Multi-Release: true` in its manifest. GraalVM polyglot 25.x ships Multi-Release JARs (`META-INF/versions/{9,21}/…`); Shadow preserves the versioned classes but drops the manifest attribute, so the JVM ignores them and Truffle throws `InternalError: Truffle could not be initialized because Multi-Release classes are not configured correctly … Multi-Release … has been lost` at `Context.build()` (PKJS never inits). Fix: `manifest { attributes["Multi-Release"] = "true" }` in `tasks.shadowJar`.
- Don't set `js.esversion` as a `GraalJsRunner` option — it isn't a valid GraalJS option and throws.
- Contexts on one `Engine` must share its HostAccess: Truffle throws `Found different host access configuration for a context with a shared engine`. Get contexts from `GraalEngines.contextBuilder`, never `Context.newBuilder` directly.
- When building JS strings to `eval` (e.g. injecting an XHR response body), JSON-encode the value (`Json.encodeToString(...)`) — don't hand-escape. Unescaped `\n`/`\r`/control chars cause a silent `PolyglotException` and the JS callbacks never fire.

libpebble3's `GraalJsRunnerTest` (jvmTest, `:libpebble3:libpebble3:jvmTest`) runs PKJS offline on GraalJS with the real shims: bridge init, the host-access allow-list, AppMessage/config round trips, intercepted and reused XHRs, the XHR timeout, abort and session end (each closing its connection, the session's HttpClient too), every redirect hop checked (a denied hop never dialled, credentials and a POST's body across hops, the browser's hop rules, the `Host` header), the network permission enforced only while plugins are on, audio streams reaching JS as `ArrayBuffer`s, `Pebble.permissions.query` (answered without asking, frozen), the `WebSocket` refused without the network permission (error, then close 1006, never dialled), sessions sharing the engine. Add a case there for a shim change; still confirm on hardware via `Pebble JS Bridge initialized.` and the script's `console.log` output in the log.

## Deployment (postmarketOS / systemd user service)

```sh
sudo install -Dm644 build/libs/stoandl-*.jar /usr/lib/stoandl/stoandl.jar
sudo install -Dm644 packaging/stoandl.service /usr/lib/systemd/user/stoandl.service
systemctl --user daemon-reload
systemctl --user enable --now stoandl
```

The service unit sets `DBUS_SESSION_BUS_ADDRESS=unix:path=%t/bus` so it finds the user session bus without a graphical login.

## GUI / D-Bus contract

The daemon's public control surface — for the CLI and the GUI (the `gui/` submodule, a Kirigami
front-end) — is the single D-Bus interface `de.yoxcu.stoandl.Control` (session bus,
name `de.yoxcu.stoandl`, path `/de/yoxcu/stoandl`), defined in `dbus/StoandlControl.kt` and implemented
by `StoandlControlImpl` in `PebbleIntegration.kt`. The **methods are the source of truth**; eleven
signals (`WatchesChanged`, `FirmwareProgress`, `LockerChanged`, `LanguageProgress`, `CalendarsChanged`, `PluginsChanged`, `PermissionRequestsChanged`,
`ExtensionsChanged`, `ExtensionStateChanged`, `ConfigChanged`, `TaskChanged`) are a reactive layer on top, and there are no properties.
The daemon isn't D-Bus-activated, so a client can miss a signal: it re-reads the method when the name
appears and keeps a slow fallback poll. Long-running ops (pair, firmware flash, language install, the watch
tasks: sideload, screenshot, logs, core dump) report progress via polled status strings
(`PairStatus`/`FirmwareStatus`/`LanguageStatus`/`TaskStatus`), which the CLI uses. `backup`, `restore` and
`support` are **CLI-local** (no D-Bus method). The CLI exits 0 done, 1 failed, 2 usage, 3 daemon unreachable
(`ctlError` in `Main.kt`). The GUI's settings pages (one per schema `page` column) render whatever
`GetConfigSchema` advertises (`config/ConfigSchema.kt`), so a new config key needs a schema row, not GUI code:
its page and section, a one-sentence `desc` (at most 90 characters), `help` for what the description leaves
out, `requires` only for a hard gate (the row does nothing otherwise), and `egress` naming every host it makes
stoandl contact (such a row must default off; `ConfigSchemaTest` enforces it), plus its line in
`packaging/stoandl.conf.example` at its default. Then regenerate the GUI mock's fixture
`gui/tools/config-schema.tsv` (and `watch-pref-text.tsv` after a watch-pref text change) with
`STOANDL_UPDATE_GOLDEN=1 ./gradlew test --tests '*ConfigSchemaTest*' --tests '*WatchPrefTextTest*'` (in the
container through `stoandl-check-locked.sh`, then copy them from `.cache/stoandl-build/gui/tools/`), commit them
in gui and bump the gitlink.

See [docs/dbus-interface.md](docs/dbus-interface.md) for the full method catalog (D-Bus signatures,
CLI mapping, tab-separated record layouts, status-string conventions, exit codes) **and** the GUI gap analysis
per screen (Watch, Apps & Faces, Plugins, Settings, System). Keep that doc in sync when you change the
interface.
